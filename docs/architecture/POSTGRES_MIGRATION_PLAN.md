# PostgreSQL Migration Plan

Replace MySQL 8.0 with PostgreSQL 16 across the entire `sunwinkr-backend` stack. The USDT gateway (`sunkr-usdt-gateway`) is already on Postgres (`Npgsql.EntityFrameworkCore.PostgreSQL` 8.0) and is excluded from scope.

> **Status:** plan only. No work started. Owner: TBD. Target window: 5–7 months from kickoff. Companion to [`LEDGER_HARDENING_ROADMAP.md`](LEDGER_HARDENING_ROADMAP.md).

---

## 1. Why

The ledger spec calls for `SERIALIZABLE` isolation, deferrable `CHECK` constraints, real `JSONB` indexing, `LISTEN/NOTIFY` for outbox, and partial indexes — all of which MySQL 8 does poorly or not at all. Beyond the ledger, every drift incident this year (May-2 agent FK, May-6 wallet drift, GSC void recreation) traces back to MySQL semantics that Postgres would have caught at write time.

We've already proven Postgres in the USDT gateway (running for 6 months, zero drift incidents). This plan extends that to the rest of the stack.

## 3. Architecture — CDC-shadow approach

```
┌─────────┐   binlog    ┌──────────┐   stream    ┌──────────┐
│  MySQL  │────────────▶│ Debezium │────────────▶│ Postgres │
│ (truth) │             │  + sink  │             │ (shadow) │
└─────────┘             └──────────┘             └──────────┘
     ▲                                                 │
     │ all apps still read/write here during soak      │ shadow reads
     │                                                 │ (sample-based)
     └─────────────────────────────────────────────────┘
                    nightly diff job
```

- Apps continue to read/write **MySQL only** through Phases 1–6.
- Postgres is kept current via Debezium CDC. The app never sees Postgres latency.
- A nightly diff job samples random rows from each table and asserts byte-equality.
- Cutover (Phase 7) is a brief write-pause + drain CDC + flip JDBC URL + reverse CDC the other way for rollback insurance.
- Rollback during the 2-week post-cutover window is a single config flip back to MySQL — both databases stay current via reverse CDC.

## 4. Phased timeline

Total: **22–28 weeks** from kickoff to MySQL decommissioned.

### Phase 0 — Audit (1 week)

Build `scripts/pg-migration-audit.sh` that catalogs every MySQL-specific construct:

- `ON DUPLICATE KEY UPDATE` → `INSERT … ON CONFLICT … DO UPDATE`
- `INSERT IGNORE` → `INSERT … ON CONFLICT DO NOTHING`
- `REPLACE INTO` → `INSERT … ON CONFLICT … DO UPDATE`
- `GROUP_CONCAT(x)` → `string_agg(x, ',')`
- `FROM_UNIXTIME(n)` → `to_timestamp(n)`
- `UNIX_TIMESTAMP(t)` → `extract(epoch from t)`
- `IFNULL(a,b)` → `COALESCE(a,b)` (MySQL accepts both, Postgres only the latter)
- `DATE_FORMAT(t, fmt)` → `to_char(t, fmt)` with format-string translation
- Backtick-quoted identifiers → double-quote identifiers (or remove)
- `AUTO_INCREMENT` → `GENERATED BY DEFAULT AS IDENTITY` or `SERIAL`
- `UNSIGNED` integer types → `CHECK (col >= 0)` or `bigint`
- `ENUM('a','b')` → `CREATE TYPE … AS ENUM` or `text` + `CHECK`
- `JSON` → `JSONB`
- `LIMIT n,m` (offset-comma form) → `LIMIT m OFFSET n`
- `FOR UPDATE NOWAIT` → same syntax (Postgres has it)
- `FOR UPDATE SKIP LOCKED` → same syntax (Postgres has it since 9.5)
- `CREATE TABLE … PARTITION BY RANGE` syntax differences
- `utf8mb4_general_ci`, `utf8mb4_unicode_ci` collations → Postgres has no `_ci`; need `LOWER(col) = LOWER(?)` or `citext` extension
- `TINYINT(1)` used as boolean → Postgres `boolean`
- Implicit string-to-number coercion (Postgres is strict)
- Group-by laxity (MySQL allows non-aggregated select columns; Postgres requires them in GROUP BY or aggregate)
- Identifier case: MySQL Linux is case-sensitive on table names by default, Postgres folds unquoted identifiers to lowercase — force consistent lowercase everywhere

Output: a CSV with `file:line | construct | suggested-replacement | risk-level`. This becomes the work breakdown for Phase 4.

**Deliverable:** `pg-migration-audit-2026-MM-DD.csv` with row counts per construct.

### Phase 1 — Provision (1 week)

- **Postgres 16** primary + 1 streaming replica, on the same Docker host network the rest of the stack uses.
- **PgBouncer** in transaction-pooling mode in front of primary. App pools through PgBouncer; Postgres `max_connections` stays low (200), HikariCP per-service pool size unchanged.
- **pgBackRest** for WAL archiving + PITR. Full + incremental schedule mirroring current MySQL backup cadence.
- **Monitoring**: pg_stat_statements + pgBadger + Prometheus `postgres_exporter`. Dashboards mirroring our current MySQL Grafana.
- **Tuning baseline**: shared_buffers = 25% RAM, effective_cache_size = 75%, work_mem per spec, autovacuum aggressive on hot tables (`money_entry`, `log_money_user_vin`, `gsc_bets`, `rebate_logs`).

Open decisions before this phase starts:
- Self-hosted on the same VPS, or managed service (RDS / Cloud SQL / Neon)? Cost vs ops trade.
- HA topology: streaming replica + manual failover, or Patroni cluster, or managed-service-handles-it?

### Phase 2 — Schema port (3–4 weeks)

For each of the 4 MySQL schemas, produce a Postgres DDL equivalent:

1. **Initial bulk via `pgloader`.** It auto-handles types (TINYINT(1)→bool, JSON→JSONB, ENUM→type, AUTO_INCREMENT→sequence) and is the fastest way to get a structurally-correct first cut. Output is the starting point, not the finished schema.
2. **Hand-fix the diffs.** pgloader doesn't know our intent for things like `utf8mb4_general_ci` (drop, force `LOWER()` at query sites) or partition definitions. Walk the diff manually.
3. **Rewrite `post_money_transaction` SP in plpgsql.** This is the only stored procedure in the money path; it's small (~80 lines) but load-bearing. Mirror the `'UNBALANCED_ENTRIES'` raise and the same atomic semantics. Add unit tests via `pg_regress`.
4. **Foreign keys + indexes.** Re-validate every FK; Postgres enforces them more strictly than MySQL InnoDB defaults (no silent ignore on missing referent).
5. **Triggers.** The `users.nickname-immutable` trigger and any others — port to plpgsql.
6. **Views.** `v_money_account_drift`, `v_money_unbalanced_transactions`, etc. — most port unchanged, audit `IFNULL`/`DATE_FORMAT` usage.

**Deliverable:** `migrations-postgres/` directory with one ported file per current MySQL migration, plus a fresh-schema bootstrap SQL.

### Phase 3 — CDC bootstrap (2 weeks)

- **Debezium MySQL connector** reading the binlog (we already have binlog enabled — `gtid_mode=ON`, `binlog_format=ROW` confirmed). Outputs change events.
- **Sink:** Kafka Connect JDBC sink → Postgres. (Alternative: ditch Kafka, use Debezium server mode → Redis Streams → custom JDBC sink. Saves an infra dep, costs a wheel-reinvention. Lean on Kafka unless the team objects.)
- **Initial snapshot:** Debezium does this automatically (locks a moment, dumps every row, then catches up via binlog). For our largest tables (`log_money_user_vin` ~50M rows, `gsc_bets` ~30M) this takes ~2 hours.
- **Catch-up SLA:** target replication lag p99 < 5 seconds. Anything more and the Phase 5 diff job will alarm on transient drift.

**Deliverable:** Postgres in continuous sync with MySQL. `SELECT NOW() - last_change_at` is checked every minute; > 60 seconds pages.

### Phase 4 — Per-service application audit (4–6 weeks)

This is the bulk of the work. For each stack, produce a service-by-service PR series. **No service flips reads/writes in this phase** — the goal is purely to make every query work against either backend.

#### Java (largest surface — 48 files flagged)

Per service:
1. Replace MySQL-specific SQL with portable equivalents (per the audit CSV from Phase 0). Verify against MySQL — must keep working in production.
2. Add a `pg-test` Gradle task that runs the same query suite against a local Postgres container.
3. Driver swap is config-only (`db_pool.properties`) — held until Phase 6.

Critical files per the audit:
- `VinPlayDAL/.../rebate/RebateService.java` — uses `IFNULL`, `GROUP_CONCAT`, `DATE_FORMAT`, has the new `appendBotFilter` helper that's already portable
- `VinPlayDAL/.../service/MoneyGateway.java` — uses `ON DUPLICATE KEY UPDATE` in cache writes
- `VinPlayDAL/.../dao/impl/UserDaoImpl.java` — `INSERT IGNORE` on user-create races
- `api/vbee/.../LogMoneyUserExtraProcessor.java` — already portable after the SUN-1248 changes
- `VinPlayUserCore/.../auth/*` — case-insensitive nickname lookups via collation; need `LOWER()` rewrite

#### PHP

- `www/agency-php/` (Laravel 8): swap `'mysql' => 'pgsql'` in `config/database.php`. Eloquent's query builder is portable; the only places that break are raw `DB::statement` calls — audit and rewrite.
- `../sunkr-admin/` (CodeIgniter 3): biggest unknown. CI3 query builder is mostly portable; raw `$db->query()` sites need the same audit. Open ticket with admin team to do their own pass.

#### Node

- `api-xsmb-today-main/`: swap `mysql2` → `pg`. Single service, ~3 query sites. <1 day of work.

#### .NET BanCa

- `banca/BanCaLiteNet/`: audit needed. If it talks to MySQL directly (rather than through the Java backend), swap `MySql.Data` → `Npgsql`.

**Deliverable:** every service's CI passes against both MySQL and Postgres. No production behavior change.

### Phase 5 — Read-shadow soak (2–3 weeks)

Run the nightly diff job:

```sql
-- For each table, every night:
WITH sample AS (
  SELECT id FROM mysql.<table> TABLESAMPLE SYSTEM (1)
)
SELECT id FROM sample WHERE
  (SELECT md5(row_to_json(m)::text) FROM mysql.<table> m WHERE m.id = sample.id)
  != (SELECT md5(row_to_json(p)::text) FROM postgres.<table> p WHERE p.id = sample.id)
LIMIT 100;
```

Any diff → page. Cause is almost always a MySQL-only construct in a writer that we missed in Phase 0. Fix forward, re-run.

Concurrently, update select read-only call sites to read from Postgres (with MySQL fallback) for production load testing — start with `c=303` history reads, agency `c=9541` rolling, admin reports. Watch latency dashboards. **Reads only; no writes touch Postgres yet.**

Exit criteria: 7 consecutive nights of zero diff and Postgres reads at parity p99 latency.

### Phase 6 — Per-service write cutover (4–6 weeks)

Cut over **one service at a time**, in this order (least-to-most risk):

1. Lottery scraper (Node) — single writer, idempotent, low volume
2. Admin portal — internal users only
3. Agency portal — agents only, can pause briefly
4. VinPlayBackend (admin API) — internal
5. VinPlayPortal (player API) — high volume, but stateless
6. Game servers (one game at a time) — stateful, BitZero framework
7. **vbee** (RabbitMQ consumer + ledger writer) — last, highest risk, holds the SP

Per-service cutover:
1. Pause writes briefly (5–60 seconds depending on service).
2. Wait for Debezium to drain (lag → 0).
3. Flip the service's `db_pool.properties` JDBC URL to Postgres.
4. Restart the service.
5. **Reverse the CDC direction for that service's tables** — Postgres → MySQL — so MySQL stays current and rollback remains a single flip.
6. Watch for 24 hours. Alarm thresholds: error rate, latency, drift-job diff.
7. If clean, proceed to next service.

The only service that's tricky is vbee, because the ledger SP has to be live on whichever DB is the writer. Sequence: deploy plpgsql SP to Postgres ahead of vbee cutover, then vbee flips, then drop the MySQL SP after the rollback window.

### Phase 7 — Rollback insurance window (2 weeks)

After all services have flipped, MySQL keeps receiving every write via reverse CDC. Drift-job runs in both directions. If anything breaks, single config flip per service brings it back to MySQL (which is current).

Exit criteria: 14 consecutive days zero diff, zero rollback events.

### Phase 8 — Decommission MySQL (1 week)

1. Stop reverse CDC.
2. Final consistency check (full-row checksum, not sample).
3. Snapshot MySQL to cold storage (S3 / equivalent), keep for 1 year.
4. Stop MySQL containers.
5. Remove MySQL from `docker-compose.database.yml`, `.env`, `db_pool.properties` templates.
6. Remove `mysql:mysql-connector-java` from Gradle. Build green.

## 6. Risks

**Highest:**
- **Implicit MySQL coercion sites** — `WHERE int_col = '5'` works in MySQL, fails in Postgres. The audit catches the easy ones; type-mismatch bugs in business logic only show up under load.
- **`utf8mb4_general_ci` collation behavior** — usernames/nicknames compared case-insensitively today. Postgres needs `LOWER()` rewrites or the `citext` extension at every comparison site.
- **Group-by laxity** — every `SELECT a, b, SUM(c) FROM t GROUP BY a` in Java code where `b` isn't grouped is a Postgres failure waiting in production.
- **Stored procedure semantics** — `post_money_transaction` is the keystone; its plpgsql version must produce byte-identical `money_entry` rows for given input. Test with full production-mirror dataset.

**Medium:**
- **HikariCP pool tuning** — Postgres connections are heavier than MySQL connections. Plan PgBouncer in transaction mode; expect to halve per-service `maximumPoolSize`.
- **Debezium snapshot lock** — initial snapshot on the 50M-row `log_money_user_vin` table holds a global read lock briefly. Schedule for 03:00 KR.
- **Foreign-key enforcement strictness** — Postgres won't silently accept FK violations. Phase 5 diff job will surface any sloppy MySQL data.

**Low:**
- **Connection-string format** — different but well-documented.
- **Time-zone handling** — both DBs store in UTC, Postgres has stronger `timestamptz` semantics. Code already uses UTC consistently.

## 7. Cutover playbook (per-service)

```
T-30m   Announce cutover window in #ops
T-15m   Confirm Debezium lag < 1s. Confirm diff job 0 results last 24h.
T-5m    Set service to read-only or pause (depends on service).
T-2m    Wait for Debezium to drain (lag → 0).
T-0     Flip db_pool.properties → Postgres URL.
T+0     Restart service.
T+1m    Watch /health, error logs, latency dashboards.
T+5m    Sample read sanity check: known query returns expected row.
T+10m   Resume traffic. Watch for 1h.
T+1h    Decision: keep or rollback. If keep, enable reverse CDC for this service's tables.
T+24h   If clean, mark service ✅ in tracker.
```

## 8. Rollback playbook

```
1. Flip db_pool.properties → MySQL URL.
2. Restart service. (MySQL is current via reverse CDC.)
3. Pause forward CDC for that service's tables (prevents corrupting Postgres while we diagnose).
4. Page incident commander.
5. Diagnose with both DBs frozen at known states.
```

If multiple services need rollback simultaneously, do them in reverse cutover order (most-risk-first, since vbee was last to flip).

## 9. Open decisions before kickoff

1. **Hosting** — self-hosted on the same VPS, managed RDS/Cloud SQL, or Neon? Cost vs. ops surface.
2. **HA topology** — streaming replica with manual failover, Patroni cluster, or managed-service-handles-it?
3. **Postgres version** — 16 (current LTS) or 17? Stick with 16 unless 17 ships a feature we need.
4. **Kafka in scope?** — Debezium can run in server mode → Redis Streams → custom sink, avoiding Kafka. Faster but less standard. Pick one.
5. **Staging mirror** — clone production to staging-Postgres for the full Phase 5 soak before touching production.
6. **Window** — when in the year? Avoid the lunar new year traffic spike, sports-calendar peaks, and any pending GSC integration changes.
7. **Per-service ownership** — assign the backend, PHP, admin, game-team, and infra leads now.
